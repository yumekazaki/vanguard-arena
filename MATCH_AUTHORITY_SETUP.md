# Online player identity and authority migration status

This migration hardens player identity and command direction for Supabase Realtime rooms. It does not make the game reducer server-authoritative yet: the host browser still validates and applies accepted commands.

1. Enable Authentication → Sign In / Providers → Anonymous Sign-Ins in the Supabase project.
2. Run the existing supabase/match-rooms.sql setup first if it has not been installed.
3. Run supabase/match-auth-v1.sql in the Supabase SQL Editor.
4. Keep the publishable key in the browser config. Never put a service-role key in the site.

Each player gets a separate anonymous Supabase session for matches, even when signed out of their account. The database binds the host and joining player to separate auth user IDs. The joining player publishes only to the guest-to-host channel and subscribes to the host-to-guest channel; the host uses the opposite pair. The client waits until both directions are subscribed before treating the relay as connected. Spectator traffic remains on its separate public, redacted snapshot topic.

Rooms created before the migration do not have an authenticated host seat and cannot use the new player relay. Create a new room after installing the migration. Older PeerJS rooms remain on their existing direct connection path and do not gain this relay authorization.

The remaining multiplayer work is to move canonical match state and the rule reducer to a trusted server, then have both clients submit versioned commands and receive owner-only decisions from that reducer. The current migration proves room-seat identity and direction; it does not validate whether a game action is legal under Vanguard rules.

## Server-owned state boundary

`supabase/match-authority-v1.sql` adds private canonical-state and command tables, a seat-checked `submit_match_action` RPC with stale-version, duplicate-ID, and one-in-flight-command checks, plus service-role-only initialization and commit/reject RPCs. `supabase/match-authority-v2.sql` adds an expiring, single-worker lease for queued commands. The worker claim returns the authenticated actor UID, both seated UIDs, canonical state, version, and a lease token; commit/reject requires the unexpired token. Database tables are not readable or writable by browser roles. Command payloads cannot supply their own actor, match, action ID, or expected version.

This is a secure storage and transaction boundary, not a complete server reducer. The static website does not call these RPCs, and no trusted worker currently initializes state, validates/reduces commands, or sends private ability decisions. Keep using the existing room migration setup only; do not treat these authority migrations as a live-game upgrade until the worker and client cutover are implemented and tested. Never place a Supabase service-role key in the browser.

The next implementation stage is a trusted server worker that obtains the command actor from the authenticated database row, loads the matching canonical state, applies the shared legality/effect engine, and commits accepted state or a rejection atomically using the lease token. It must publish public snapshots separately from player-only decisions. Full online authority remains unfinished until both clients use that path and no client can mutate canonical state.

## Trusted reducer progress

`ability-server-reducer.js` resolves the authenticated actor from the room seat and a persisted host/guest-to-game-side mapping, runs the shared ability decision/readiness checks, and resolves an allowlisted set of AUTO effect programs on a cloned state before committing. It currently supports Engorge plus basic draw, source power/critical, rest/stand, Counter-Charge, Soul-Charge, and source-to-Soul effects. It rechecks the exact source instance, controller, compiled definition identity when available, structured triggering event, source window, costs, and duplicate action IDs; rejected costs leave state unchanged. Unsupported effect operations fail closed. These are reducer primitives only: this list is not a claim of complete card support.

The worker also accepts a separate `manual-ability-activation` command for reviewed ACT definitions registered in the trusted server bundle. It resolves the ability by card ID and definition ID on the exact controlled field instance, permits only the controller during their Main phase, checks the printed circle, current usage and resource availability, and resolves costs/effects transactionally. ACT requirements or choices that are not modeled are rejected. Regression coverage exercises the joining player's legal activation, forged host activation, wrong timing, and missing resources. The static website does not submit this command yet.

The trusted reducer supports authenticated pre-match roll, winner's first-player choice, and each player's opening-hand mulligan in first-player order. Returned cards go to the bottom, replacement cards are drawn, and the deck is securely shuffled only when at least one card was returned. It also supports versioned game actions for Draw-phase draw, ride, call, attack declaration, guard/no-guard, drive-count selection (0–10), drive checks, trigger choices, battle resolution, damage checks, phase advance, and turn end. It validates seat, turn, phase, exact card instances, targets, costs, and battle identity for the implemented paths, and emits structured events for the AUTO scanner. Checked cards stay in the trigger zone through trigger resolution; damage and battle completion wait for pending effects. This is still a limited action set: many Vanguard actions, rule actions, effects, and timing windows are not implemented. The website does not yet send these commands to the trusted worker, so live online rooms continue to use the host browser as reducer.

Ability-resolution events returned by the server reducer are normalized into immutable event envelopes with unique match event IDs, the exact source and affected card instance IDs, owner/controller IDs, location changes, turn player, phase, and resolution timing. The reducer scans those events against registered, reviewed AUTO definitions and queues only exact source/event matches whose conditions can be evaluated from canonical state and whose costs, choices, and effect operations are supported. Unsupported condition types and required metadata that is absent fail closed. Prompt side is mapped from the card's controller identity, separately from the side holding the card instance. Event/card/ability claims prevent the same trigger from being queued twice. The scan repeats after each supported ability resolution, so effect-generated events can create the next pending prompt; the server still does not automatically resolve mandatory trigger chains or implement rule-based order choices for simultaneous effects.

`supabase/functions/match-worker/` contains an Edge Function endpoint and a claim/reduce/commit worker core. The endpoint validates the caller's Supabase bearer token, confirms that caller is the host or joining player in the requested room, then claims one action using the service-role-only lease RPC. It takes actor identity from the claimed database row, requires canonical `authoritySeats` mapping, validates canonical match/version/player/card-zone structure and unique card instance IDs, reduces supported commands through the trusted reducer, and completes the action using the returned lease token. Watchers and non-seated callers are rejected before command processing. Unsupported actions, malformed state, or missing seat mappings are rejected without mutating match state. The endpoint requires `SUPABASE_URL`, `SUPABASE_ANON_KEY` (or `SUPABASE_PUBLISHABLE_KEY`), and `SUPABASE_SERVICE_ROLE_KEY` as server environment values; it never places the service key in browser code. Local worker and reducer tests cover accepted commit, rejection, no-claim, lease failure, both player seats, stale state, invalid choices, duplicate requests, exact trigger-event checks, malformed canonical state, and the room-seat authorization check.

This worker is not deployed or invoked by the current website. Canonical state initialization still has no client/server flow that writes `authoritySeats`; neither client submits actions to the authority RPC or invokes this endpoint; no public snapshot or owner-only prompt delivery is wired; and the static site's room flow remains host-browser authoritative. The worker does process the events generated by its supported commands through reviewed AUTO discovery, but many actions/effects remain unsupported. Do not advertise server-authoritative online play until canonical initialization, client submission/invocation, private/public synchronization, broader action reduction, and both-client cutover are implemented and tested.

`match-authority-client.js` now provides a tested browser transport helper that submits an action with its expected state version, invokes `match-worker` using the authenticated caller's Supabase client, then reads that caller's action result and projected state. It rejects client-supplied actor/match/action/version fields and supports retrying a queued duplicate if the worker invocation previously failed. Its allowlisted action-payload builder rejects unsupported legacy actions and untrusted extra fields; separate builders bind manual ACT requests and AUTO responses to exact card-instance and ability IDs while rejecting nested forged identity fields; its state watcher delivers only newer caller-projected versions without overlapping polls. These helpers are not yet loaded or called by `app.js`; they are transport components, not a claim that the website has switched to canonical state.

The trusted reducer now also processes reviewed opponent-target retirement, the Revelation optional Soul/rest sequence, Stride, reviewed continuous power during battle declaration, continuous shield while guarding, an exact Rear-Guard stand target, Great Daiyusha and Perfect Raizer continuous critical, and Soul-count continuous power for Perfect Raizer, Artilleryman, Rhodia, and Baromagnes. These conditions use exact source circles, current controller Soul, and printed own-turn requirements. Stride checks the active phase, timing/grade eligibility, exact owned face-down G Unit, and exact owned hand costs before mutation; standard costs use grade totals and reviewed continuous Stride-grade modifiers, while Ultimate Stride uses its separate same-name payment rule. A reviewed ability with a nonzero printed index is now reconstructed from its exact trusted definition instead of being lost when its isolated text parses at index zero. Continuous power and critical check the exact source's trusted ability definition and legal circle. Guard resolution adds the guard's reviewed Guardian Circle shield modifier to printed shield before updating defense. The cfa-41 stand AUTO targets the exact eligible friendly Machining Rear-Guard and is consumed without a prompt when no legal target exists. Reducer tests verify invalid Stride payments leave state unchanged, the worker commits the joining player's legal Stride, Cycloned's 5,000 power applies only to a friendly abilityless unit without a manual prompt, Harshiel receives its conditional Guardian Circle shield, Great Daiyusha and Perfect Raizer get their critical only with the required conditions, Perfect Raizer's Soul power is included in its attack, and Steam Breath Dragon's grade modifier works for the joining player. The complete repository suite passes 494/494 (37.96 seconds). This does not complete the action or card pool: app wiring, live canonical initialization, private/public state delivery, broader card coverage, and live multiplayer validation remain outstanding.

The client snapshot projection now hides each opponent's hand, deck order, and G-deck identities while preserving card counts. Spectator snapshots hide both sides' identities in those zones. This is defense in the relay projection only: the host's browser still holds the complete match state, so it is not a security boundary against the host and does not replace canonical server state.

`match-bootstrap.js` now provides a shared, deterministic-shape starting-state builder for two authenticated deck submissions. It validates card IDs/counts, the selected Grade 0 starter, 50 main-deck cards, 16 triggers, current copy/Sentinel/Heal/Over/Regalis/G-deck limits, then creates distinct owner/controller-stamped instances, shuffles with an injectable secure random source, and emits `authoritySeats`. Its tests validate the result against the worker's canonical-state gate. This builder is not yet called by a server initializer: although v3 adds private deck storage, the Edge Function still lacks the licensed card catalog and an authenticated setup flow.

`supabase/match-authority-v3.sql` adds private per-seat deck registration. An authenticated player can submit or replace only their own deck before initialization; clients cannot read the submissions. A service-role-only RPC returns both decks only after both seats submit and locks them against further edits. The host and joining-player room flows now call the player-only submission RPC with their selected deck; errors are non-fatal and leave the existing relay flow available. This is a private submission step only: the host browser still starts the match and neither client invokes server initialization. Its SQL contract has static regression coverage, but has not been applied to Supabase or exercised against PostgreSQL.

`match-initializer.js`, `supabase/functions/match-initialize/`, and `supabase/match-authority-v4.sql` add a trusted initializer path. It authenticates the caller against a room seat before claiming either deck, fetches definitions only from a service-role-only catalog whose rows are explicitly marked for redistribution, validates both decklists with the existing bootstrap, builds unique owner-stamped state, and asks SQL to compare the resulting card multiset with the current submissions while locking and inserting state atomically. This avoids trusting card details supplied by the browser and avoids permanently locking a submitted deck before card catalog and deck validation succeed. Tests exercise authorized/unauthorized callers, legal/illegal decklists, missing catalog rows, exact state commit, and the v4 SQL contract.

This path is not production-ready or wired into the website yet. The currently tracked catalog marks its data “Personal local use,” so it must not be copied into a server catalog for public hosting without separate redistribution authorization. The v4 table intentionally returns only rows with `redistribution_authorized = true`; an appropriately licensed catalog import must be provided. Apply v4 only after that data source is available and the SQL has been reviewed against a live PostgreSQL/Supabase project. The Edge Function also needs deployment, and both clients still need a canonical-state subscription/cutover before invoking initialization; creating a server match while continuing to play a separate host-browser match would be incorrect.

`supabase/match-authority-v5.sql` adds authenticated player reads for canonical state and action results. State reads map the room seat to its canonical side, redact the opponent's hand/deck/G-deck identities and face-down damage, and omit ability/cost prompts owned by the other player. Action results are scoped to the authenticated action submitter. The JavaScript projection helper and SQL-contract tests cover those privacy boundaries. The SQL has not been applied to Supabase, and no client polls these RPCs yet.
