# Vanguard ability categories for catalog verification

This project uses the ability categories in the supplied Comprehensive Rules excerpt to organize implementation and review. The category is a processing and timing distinction; it does not by itself prove that a card is supported.

| Category | Engine treatment | What the definition must preserve |
| --- | --- | --- |
| `ACT` | A player explicitly activates it during a legal window. A costless ACT still requires a player action. | Controller, zone, timing, conditions, cost, usage limit, choices, and effect order. |
| `AUTO` | A structured game event or timing window makes it eligible. The exact source instance and trigger event must match. | Event, source/subject identity, timing, optionality, costs, requirements, choices, and resolution order. |
| `CONT` | Recomputed as a continuing rule while its location and conditions apply. It does not open an activation prompt. | Active zones, conditions, affected cards, modifiers/restrictions, and when the effect ends. |
| `ORDER` | The order card's printed instruction resolves through order play, even without an ACT/AUTO/CONT icon. | Play window, cost, modes, targets, operation order, and destination/cleanup. |
| `TRIGGER` | A drive-check or damage-check ability uses the shared trigger rules for its trigger type. | Trigger type, checking player, timing, eligible target/choice, and standard effect. |

## AUTO requirements and timing

The rules distinguish the event that makes an AUTO eligible from its requirements during resolution. For wording such as `When [event], if [requirement]`, the event can make the AUTO eligible even when the requirement is currently false. Our intended UI policy is to avoid prompting while the requirement is false, retain a hidden pending item only while another pending ability could change that requirement, recheck it after that ability resolves, and consume it as a no-op if it remains false when the resolution window closes. The current engine has this behavior only for explicitly reviewed ability families; general AUTO requirement-scope handling remains unfinished.

Requirements are scoped by the printed sentence and sequence. A condition does not automatically gate every later sentence. A `Then` clause depends on the preceding clause as specified by the rules. The parser must keep this scope explicit; ambiguous or unsupported wording remains pending review.

## Verification and the fast path

The category inventory is generated by:

```powershell
node scripts/build-ability-category-inventory.js --output .card-pipeline/ability-category-inventory.json
```

It counts the catalog's explicit ability blocks and separately identifies order and trigger cards, which are not all represented as icon-labeled blocks by the current parser. It also groups repeated compiled patterns to help prioritize shared handlers. Trigger types come from the structured card field first, then explicit printed text (including plural labels); records without a reliable type are listed for review instead of guessed. The inventory is triage data only: it never marks a card or ability verified.

## Measured catalog coverage

For the current 2025-05-09 catalog snapshot (14,022 cards; generated 2026-11-07), the parser identifies 11,589 AUTO, 2,255 ACT, and 3,410 CONT ability blocks. The card-level inventory also finds 473 Order cards and 1,951 Trigger cards; five Trigger cards have no reliably recognized trigger label. These counts describe classification coverage, not implementation coverage.

Shared handlers may be reused only when the source text has the same rules meaning. Each card definition still needs its original text, exact ability ID, supported requirements/costs/choices/effects, and evidence. A whole card remains unverified until every printed ability has been reviewed and tested against the authoritative text and applicable rules.

## Keyword triage index

Generate a literal keyword index for every parsed ability with:

```powershell
node scripts/build-ability-keyword-index.js
```

The ignored output is `.card-pipeline/ability-keyword-index.json`. It records ability kind, visible zone cues, costs, restrictions, condition/effect words, source-specific AUTO trigger cues, implementation state, and existing ability-level evidence. Its grouped signatures are workload triage only: a shared trigger or shared word such as `draw`, `boost`, or `power` does not establish that two effects are equivalent. Multi-cue text is marked ambiguous and unmatched AUTO wording is left unclassified. This index never creates definitions, changes runtime behavior, or promotes cards.

The current cue pass indexes one literal event for 7,631 AUTO blocks, flags 146 multi-cue blocks for review, and leaves 3,812 without a single recognized cue. Before adding short-form placement, being-ridden, source-drive-check, boosted-target, and related event cues, 6,159 blocks had one cue and 5,331 were unclassified. This reduced the unclassified share while retaining separate ambiguity flags; it did not change the catalog parser or game runtime.

The latest index exposes 740 exact printed-text families spanning 4,073 ability rows (ability kind retained; whitespace normalized only). Each group can share one text-level rules review, followed by exact-ID checks for every card. Literal keyword tags include mechanic cues such as Sentinel, Forerunner, Generation Break, Limit Break, Harmony, Hollow, and Persona Ride. A keyword tag is not an interpretation of the effect and does not count as verification.

The index now includes literal cues for all 61 keyword terms mapped from the supplied Comprehensive Rules section 14 (58 numbered headings, with combined terms such as Twin/Triple Drive and Seek Mate/D-Seek Mate split into separate tags). In the 2025-05-09 catalog snapshot, 5,538 ability blocks match at least one cue. The generated `keywordMechanicCoverage` table ranks those cues by ability count, compiled definitions, and existing passing evidence so reusable mechanics can be prioritized. These are text matches only: common words such as `charge`, `boost`, and `oracle` can also occur outside the corresponding keyword ability, so the counts guide review and never establish support or verification.

The latest strict whole-card gate kept the three Sweat16! Counter-Charge cards unverified because their imported wording still needs official card-text confirmation. It also promoted Dudley Daisy (`cfa-607:0`) and Dudley Douglass (`cfa-614:0`): both have a single printed ability, official card-list wording, exact structured definitions, and passing host/joiner regressions. The current generated snapshot contains 4,746/17,254 compiled abilities (27.50%), 12,508 unsupported or unreviewed abilities, 890 fully verified abilities, and 877 fully verified cards. The full Node suite passes 3,050/3,050 with a fresh source digest. The Crest-zone Limit Break enabler family (`cfa-12577:2`, `cfa-12580:2`, `cfa-12591:2`) and two RC-only Resist abilities remain ability-level evidence only because their cards have unfinished sibling abilities. The gate requires exact definitions, trustworthy sources, ability-specific tests, both-player coverage, and all sibling abilities before promoting a card.

An intercept cue is recorded as the exact source card moving from Rear-Guard Circle to Guardian Circle. It is distinct from an ordinary call or placement cue. The index is triage only; actual eligibility and resolution still require matching the authoritative instance transition and a reviewed ability definition.
